# 将审核方法用于团队流程

仅在用户要求设计、配置或改进仓库审核流程时读取。日常代码审核不要求先建立这些设施。先识别当前问题和已有配置，提出最小变更，在已授权范围内实施。

## 把具体失败交给合适的检查

先列出本仓库实际发生过或与当前变更直接相关的失效场景，再判断哪一层能提供有效证据。层次可组合，不是每次必须重复执行的任务清单。

| 时点 | 应解决的问题 | 可用手段 |
| --- | --- | --- |
| 实现过程中 | 代码是否满足已知行为 | 针对性测试、构建、界面对照、相关格式与静态检查 |
| 提交审核时 | 差异是否改变调用关系或引入缺陷 | 基于上下文的代码审阅、必要的独立视角 |
| 涉及安全边界时 | 权限和数据保护是否成立 | 针对实际边界的核验及项目安全检查 |
| 准备合并时 | 是否满足仓库要求 | 必需 CI、当前候选的批准、适用的分支规则 |
| 集成与发布时 | 与最新基线组合后是否正常，错误能否恢复 | 现有合并队列、分阶段验证、适用的功能开关或回滚 |
| 运行之后 | 漏检了什么，如何发现与修正 | 实际反馈、运行指标、回滚及故障记录 |

同一候选已有有效证据时，后续层只补自身需要的部分。不能自行取消仓库强制 CI 或把文档中的计划写成已配置的自动化。

## 让项目审核规则保持短小

优先复用现有 `AGENTS.md`、`CLAUDE.md`、`REVIEW.md` 和 PR 模板。确有反复出现的误判或遗漏时，更新最贴近该问题的规则；可机械验证的约束优先写入现有检查。

适合写入 `REVIEW.md` 的内容：

- 本仓库最重要的几种失败及对应代码位置。
- 哪些规则是必须遵守的，哪些只是偏好。
- 已明确不在此次审核范围的目录或生成内容，及例外条件。
- 发现必须附带触发条件、后果与证据；没有确认问题时直说零项。

PR 交接保留足够的信息：变更目的、有效验证、实际风险与恢复方式。简单修改可用几句话，不默认建立长篇报告。

## 人工批准与自动检查分开记录

读取实际 CODEOWNERS、分支规则和团队约定，不把其他公司的批准人数搬成默认规则。审核建议不会自动更改保护设置，也不会使新作者获得项目的受信资格。

新增提交、合并冲突解决或发布候选变化后，重新核对项目要求的批准是否有效。Agent 的判断不能填补必须由人完成的批准。已经获得且仍覆盖当前动作的授权也不应重复索取。

## 用结果改进审核者

流程调优时，把真实漏检、误报和正确无问题的变更整理为小型评估集。审核提示、工具或模型改变后，检查是否改善了这些案例，而不是只统计评论增加了多少。

可以观察每个工作项的审核轮数、人工等待与处理时间，以及回滚、故障和误报。未建立基线前不要宣称提速或质量改善。小任务无需额外创建统计工程。

已有代码的周期性检查应作为独立、明确授权的任务，不能塞入每轮增量复审；本 Skill 不会自行创建定时任务。与当前安全交付直接相关的严重既有问题仍须在本轮说明。

## 交付后的责任

发布安排应明确谁能处理异常、什么信号触发处置、如何恢复。检查这些安排不等于获得执行发布、回滚或更改服务配置的授权。

需要共享知识时，围绕下一位维护者将修改的模块提供简短说明或图示，并指向当前代码。方向性分歧尽早向任务负责人提出，避免把新产品需求伪装为临门的代码缺陷。
