# 审核状态与证据

同一工作项只维护一个当前状态。短审核直接放在报告中；已有任务系统或 PR 台账时复用它。以下字段按需要使用，不强制创建额外文件。

## 工作项

```yaml
work_item: example-change
intent: 本次变更要完成的用户行为
scope: 本次审阅的差异、模块或 PR
base: 审阅基线
candidate: 提交及必要的未提交文件内容标识
risk: low / medium / high
risk_reason: 具体失败后果
review_round: 1
round_limit: 3
required_checks: []
required_human_approvals: []
```

候选、范围或环境变化时保留旧记录，只更新受影响证据；不要以新建工作项来清零同一返工任务。

## 问题与证据

| 字段 | 含义 |
| --- | --- |
| ID / fingerprint | 稳定编号；根因、受影响对象、触发方式 |
| location / trigger | 位置和实际触发条件 |
| consequence | 对用户、数据、系统或项目约定的影响 |
| evidence | 源码、运行结果、测试或相关事实 |
| origin | 本次引入 / 既有 / 暂无法判断 |
| blocking | 是否阻断当前结果，理由是什么 |
| status | open / resolved / rejected / deferred |
| disposition | 修复证据、拒绝理由或允许延后的依据 |
| reopen_reason | 重新打开时新增了什么证据 |

检查证据至少能回答：检查了什么、针对哪个候选及环境、何时执行、观察到什么、覆盖范围是什么。记录实际命令与结果或可信 CI 链接，不用“应该通过”代替执行。

重跑前判断旧证据是否仍适用；判断需要相关输入，不只看提交编号。无法建立适用关系时，仅将相应检查标为缺证据。

## 结论含义

| 结论 | 何时使用 |
| --- | --- |
| PASS | 请求范围完成，必要证据有效，无未解决阻断项 |
| CHANGES_REQUIRED | 有确认的阻断问题，且当前授权与预算允许继续处理 |
| INCOMPLETE | 缺少完成请求所需的代码、工具能力或关键证据；不推断其已通过 |
| NEEDS_DECISION | 达到轮数上限、无新证据的争议或关键范围冲突，需要选择后续方向 |

`PASS` 不是零缺陷保证。只读静态检查可以给出限定范围的结论，但不得表述为运行、CI 或发布验证通过。没有读取到项目要求的批准状态，应标为未知，不猜测数量或是否已满足。

报告示例结构：

```text
确认问题：0 项；关键验证缺口：1 项。
范围 / 候选：……
审核轮数：1 / 3。
有效证据：……
结论：INCOMPLETE，仍缺……，影响……判断。
下一步：执行……检查；其余仍有效的证据继续复用。
```
